System architecture

Algorithm Visualization Project runs entirely in your browser. There is no application server: every page is built ahead of time, and your code is parsed and run on your own device.

From code to visualization

The interpreter does not animate anything. It runs your program once from start to finish and records a list of steps. Each step holds the source lines to highlight and the actions to apply, such as adding a variable or marking an array cell. The Variables pane and the visualization then replay those steps.

Stepping and editing

Because the steps are recorded ahead of time, moving backward is as fast as moving forward, and nothing runs again. Changes in the Code pane take effect only when you click Save, which runs the program again and records new steps.

for, while, and do ... while loops each stop after about 1000 iterations, with no warning. This protects the page from a simple infinite loop, but it has limits. It applies to each loop separately, so nested loops can still produce millions of steps, and for ... in loops are not limited at all. Either can slow down or freeze the page.

What stays in your browser

Your preferences, such as theme, layout, speed, and favorites, are kept in your browser's localStorage. Your code leaves your browser only when you use the AI Tutor. As with most websites, the site's host and Google Fonts receive standard request details, such as your IP address, when a page loads.

Contributors can find more detail in the architecture documentation.

Pseudocode syntax

Algorithms are written in a small pseudocode language and saved as .avp files. The first line is a title comment, followed by a blank line. The app uses that line as the page title. Every program also needs a top-level call so that it actually runs.

// Linear Search

a1 = arr[1, 10, 5, 6, 4, 7, 19]
key = 7

// Finds the first occurrence of an element in an array
fun Linear_Search(@init<table> a, k):
    n = length(a)

    for @mark<i, outline, yellow> (i = 0; i < n; i += 1):
        if (a[i] == k):
            @mark<i, highlight, green> return i
        end if
    end for

    @log<"Not found: "> return -1
end fun

result = Linear_Search(a1, key)

Open Linear Search in the visualizer to step through the bundled version.

/ is real division, so use floor(x) when you need a whole number. Array indexes are rounded down. The word arr is reserved, so it cannot be a variable name.

Control flow

Every block ends with a matching end keyword. Parentheses around a condition are optional, except in for (...) and do ... while (...). Use break to leave the innermost loop, and continue to skip to its next iteration.

if (x < y):
    ...
else if (x > y):
    ...
else:
    ...
end if

while (i < n):
    ...
end while

for (i = 0; i < n; i += 1):
    ...
end for

for item in a:
    ...
end for

A do ... while loop runs its body at least once. It ends with the while line and has no end keyword.

// Count Up

fun Count_Up(limit):
    i = 0
    do:
        i += 1
    while (i < limit)
    return i
end fun

result = Count_Up(3)

Functions and built-ins

Declare a function with fun Name(a, b): and close it with end fun. Function names should start with a capital letter. This is a convention, not a syntax rule.

Visual directives

Directives control what the visualization shows. Put one at the start of a line, before the statement it annotates, or before a function parameter. On a for loop, you can also put it right after the word for. You can chain several on one line, but a directive cannot sit on a line by itself. Directives change only the visualization, not your program's variables.

Directives on an if statement are currently ignored, with no error. Put them on a statement inside the block instead.

Use outlines for cursors and iterators, and use highlights sparingly, for found, swap, and warning states. The interpreter adds comparison text and array-access marks automatically. A hand-written text mark displays nothing, so you don't need one.

AI Tutor

The AI Tutor writes pseudocode for you. Describe an algorithm, or ask for a change to the code in your editor, and click Generate. It produces code in one shot: it does not explain its answer or hold a conversation.

How it works

The AI Tutor uses retrieval-augmented generation (RAG). Before writing anything, it looks up real pseudocode examples so that the language model can follow the syntax of this language.

  1. Prompt: The app combines the language rules, the code in your editor, and your request. If you leave the request empty, it uses the page title.
  2. Retrieve: The AI service searches its knowledge base for the 6 most similar functions, using BAAI/bge-base-en-v1.5 embeddings and a FAISS index. BAAI/bge-reranker-base then reranks them and keeps the best 2.
  3. Generate: Those 2 functions are added to the prompt as reference code, and a language model writes the result.
  4. Review: The code opens in the editor in edit mode. Nothing runs until you click Save.

Privacy

When you click Generate, your request and all of the code in your editor are sent to a third-party host and a language model provider. Keep private information out of both. Nothing is sent until you click Generate.

Check the results

AI output can be wrong, even when it runs. Read the code and step through it before you rely on it.
